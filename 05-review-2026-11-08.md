## P1. Смена статуса прямым UPDATE обходит историю и комментарий
Файл supabase/migrations/02_security_and_transitions.sql:98,178,217,320.
RLS разрешает UPDATE собственных задач исполнителю и любых задач постановщику. BEFORE UPDATE проверяет переход, но не пишет историю. История пишется только внутри RPC transition_task. Поэтому прямой PATCH tasks (new → in_progress своим исполнителем) меняет статус без истории. PATCH review → rework от постановщика проходит без обязательного комментария: проверка комментария есть только в RPC.
Исправление: запретить клиенту прямое изменение status (колоночные grants, аккуратно учесть table-level UPDATE), оставить переходы через авторизованный RPC. Либо сделать единый DB-trigger путь валидации и истории для каждого обновления; не допустить двойных записей из RPC. Проверить оба обхода прямым API, затем нормальный RPC.

## P1. Можно создать задачу сразу принятой и подменить автора
Файл supabase/migrations/02_security_and_transitions.sql:80,156.
Managers full access FOR ALL проверяет только роль. INSERT не проверяет status=new, author_id=auth.uid(), серверный created_at и роль назначенного исполнителя. AFTER INSERT сохраняет NEW.author_id как actor истории. Постановщик может через API создать status=accepted с чужим author_id; история припишет создание другому человеку.
Исправление: BEFORE INSERT устанавливает/проверяет new, auth.uid(), now(); assignee должен иметь роль executor. Начальную историю формировать от auth.uid(), а не доверять клиенту. Явно отделить административный seed от клиентского пути.

## P2. Аудит RLS в UI даёт недостоверные результаты
src/hooks/useSecurityAudit.ts:27,44,104. В Supabase-ветках аргумент currentUser не меняет JWT: запрос исполняется под текущей реальной сессией. Поэтому передача INITIAL_PROFILES[1] не тестирует настоящую сессию Александра. Любая ошибка (сеть, неверный ID, auth) засчитывается как успешный запрет. В demo тест истории начинает с rejected=true и ничего не проверяет.
Нужны отдельные реальные сессии manager/executor1/executor2, существующие fixtures, позитивный контроль доступности, проверки конкретного ожидаемого запрета и неизменности данных/истории. Ошибка сети = тест не выполнен. Пометить demo-аудит как симуляцию, а не проверку БД.

## P2. Демо не заменяет обязательный backend
src/lib/supabase.ts и AuthContext.tsx автоматически включают localStorage-режим без env. Там нет реальной изоляции: все данные хранятся у клиента. Для сдачи подключить реальный Supabase и проверить прямые API-запросы; явно подписать демо. README сейчас называет облако необязательным, хотя ТЗ требует Supabase. Отключение регистрации нужно выполнить в настройках Auth: SQL из репозитория само по себе это не доказывает.

- Проверять непустые title/name/address и допустимость assignee на уровне БД, не только UI.
- Прямое редактирование author_id/created_at постановщиком лучше запретить; эти поля — происхождение данных.
