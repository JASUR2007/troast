# Troast CRM — Мини-CRM «Объекты и задачи»

Система управления строительными объектами и задачами для 2B Studio.
Разделение ролей (**Постановщик** и **Исполнитель**), строгая матрица переходов статусов и гарантированная защита данных на уровне базы данных PostgreSQL (**Row Level Security (RLS)**, триггеры и RPC-функции).

- 🌐 **Работающее приложение (Vercel):** [https://troast-crm.vercel.app/](https://troast-crm.vercel.app/)
- 📦 **Репозиторий проекта (GitHub):** [https://github.com/JASUR2007/troast](https://github.com/JASUR2007/troast)

---

## 🛠 Стек технологий

- **Frontend:** React 18, TypeScript, Vite, Tailwind CSS, Lucide Icons, React Router DOM.
- **Backend / Database:** Supabase (PostgreSQL, Supabase Auth, Row Level Security, PL/pgSQL триггеры и функции).
- **Безопасность:** RLS-политики на каждой таблице, серверная транзакционная валидация смены статусов (`transition_task`), неизменяемый журнал истории (`task_history`).

## 🚀 Быстрый старт

### 1. Установка зависимостей и локальный запуск

```bash
# Установка пакетов
npm install

# Запуск локального сервера разработки
npm run dev
```

Приложение откроется по адресу `http://localhost:5173`.

> 💡 **Автономный демо-режим:** В приложении встроен локальный эмулятор RLS и переходов статусов с готовыми демо-данными. Вы можете сразу протестировать систему в браузере, переключаясь между ролями в 1 клик, даже без подключения к облаку Supabase.

### 2. Подключение к облаку Supabase (при необходимости)

1. Создайте бесплатный проект в [Supabase](https://supabase.com/).
2. Перейдите в **SQL Editor** в консоли Supabase.
3. Откройте файл [`supabase/full_setup.sql`](./supabase/full_setup.sql), скопируйте его содержимое и выполните (нажмите **Run**). Скрипт создаст:
   - Таблицы `profiles`, `objects`, `tasks`, `task_history`
   - Все RLS-политики
   - Триггеры защиты от прямого изменения данных
   - RPC-функцию `transition_task` с пессимистической блокировкой `FOR UPDATE`
   - 3 тестовых пользователей с паролем `TestPass123!`, 3 строительных объекта и 6 задач в разных статусах.
4. Создайте в корне проекта файл `.env` на основе `.env.example`:
   ```env
   VITE_SUPABASE_URL=https://<your-project-id>.supabase.co
   VITE_SUPABASE_ANON_KEY=<your-anon-key>
   ```
5. Перезапустите dev-сервер (`npm run dev`).

## 🔒 Архитектура безопасности и RLS

В соответствии с требованиями ТЗ, правила доступа работают **на уровне базы данных**, даже при обращении в обход интерфейса:

1. **Изоляция чтения задач (`tasks`):**
   - Постановщик видит все задачи (`public.get_my_role() = 'manager'`).
   - Исполнитель видит **только** назначенные ему задачи (`assignee_id = auth.uid()`).
2. **Изоляция чтения объектов (`objects`):**
   - Постановщик видит все объекты.
   - Исполнитель видит только объекты, где у него есть задачи (`EXISTS (SELECT 1 FROM tasks WHERE tasks.object_id = objects.id AND tasks.assignee_id = auth.uid())`).
3. **Защита от подмены полей задачи:**
   - Триггер `trg_validate_task_update` блокирует изменение полей `title`, `description`, `object_id`, `assignee_id`, `author_id`, `created_at` для исполнителя.
4. **Матрица допустимых переходов статусов:**
   - `Новая` → `В работе` (только назначенный исполнитель)
   - `В работе` → `На проверке` (только назначенный исполнитель)
   - `На проверке` → `Принята` (только постановщик)
   - `На проверке` → `На доработке` (только постановщик, **комментарий обязателен**)
   - `На доработке` → `В работе` (только назначенный исполнитель)
   - Все остальные переходы отклоняются базой (`RAISE EXCEPTION`).
5. **Защита истории (`task_history`):**
   - Прямой `INSERT`, `UPDATE` и `DELETE` через клиентский API запрещён RLS-политиками (`WITH CHECK (false)`).
   - Записи истории формируются исключительно сервером: при создании задачи (триггер) и при вызове защищённой функции `transition_task` с серверной временной меткой `now()` и авторизованным `auth.uid()`.
6. **Интерактивный тест безопасности в UI:**
   - В шапке приложения доступна кнопка **«Проверка RLS»**, запускающая набор негативных тестов к API/БД (попытка прочитать чужую задачу, изменить чужую задачу, выполнить недопустимый переход, вернуть на доработку без комментария, сделать прямой INSERT в историю).

## 📋 Список решений и допущений

1. **Терминальный статус «Принята»:** Статус `Принята` является финальным завершением жизненного цикла задачи. Повторное открытие принятой задачи в ТЗ не предусмотрено.
2. **Удаление задач:** Право на удаление задач имеет исключительно постановщик. При удалении задачи история удаляется каскадно (`ON DELETE CASCADE`), так как аудит относится к жизненному циклу удаляемой сущности.
3. **Переназначение исполнителя:** Постановщик может переназначить задачу на другого исполнителя при редактировании. При этом прошлый исполнитель автоматически теряет к ней доступ согласно RLS.
4. **Несколько постановщиков:** Система поддерживает произвольное количество руководителей; любой постановщик обладает правами проверки и приёмки работ.
5. **Открытая регистрация:** Регистрация в Supabase отключена во избежание несанкционированного создания аккаунтов клиентами.
