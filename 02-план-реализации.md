# План реализации Troast — мини-CRM
Это предложенное решение, а не дополнительные требования работодателя.

## Стек
React + TypeScript, Vite, Supabase Auth и PostgreSQL, supabase-js, React Router. Для простого UI достаточно CSS; при желании готовая UI-библиотека. Деплой Vercel. Отдельный Node/Laravel сервер для этого объёма не нужен. Версии выбрать актуальные при создании проекта, зафиксировать lock-файл.

## Модель
profiles(id = auth.users.id, display_name, role: manager/executor).
objects(id, name, address, created_at).
tasks(id, title, description, object_id, assignee_id, status, author_id, created_at).
task_history(id, task_id, actor_id, from_status, to_status, comment, created_at).
Индексы tasks(assignee_id), tasks(object_id), task_history(task_id, created_at).

## Безопасность и бизнес-логика
Включить RLS на всех таблицах. Роль хранить в защищённом profiles, не в редактируемой пользователем metadata. Не разрешать клиенту менять собственную роль.
Постановщик видит всё, управляет объектами и задачами. Исполнитель читает только назначенные ему задачи, объекты с такими задачами и историю этих задач. Проверку видимости объекта вынести в безопасную функцию или продумать политики без рекурсивных зависимостей.
Исполнитель не меняет название, описание, назначение, автора или объект. Только допустимые переходы статуса.
Смену статуса и добавление истории выполнять атомарно на стороне PostgreSQL. BEFORE UPDATE проверяет старый/новый статус, роль, assignee, защищённые поля. Историю создаёт триггер; actor = auth.uid(), время = серверное. Клиенту запретить INSERT/UPDATE/DELETE истории.
При RPC transition_task(task_id, expected_status, target_status, comment) блокировать строку FOR UPDATE, проверять expected_status и все разрешения. SECURITY DEFINER требует фиксированного search_path, явной авторизации и ограниченных EXECUTE grants. Не использовать доверенные client actor/role.
Запретить удаление истории напрямую через API; при удалении самой задачи постановщиком каскадное удаление — отдельно документируемое допущение.
Во frontend только publishable/anon key и URL Supabase. service_role не включать в env VITE_*, сборку или Git. Регистрацию отключить, пользователей создать вручную.

## Этапы на 2–3 часа
1. 0–45 минут: SQL миграции, политики, переходы и история, три тестовых пользователя.
2. 45–110 минут: вход, объекты, карточка объекта, задачи, действия и история.
3. 110–150 минут: негативные проверки через прямой API, исправления, демоданные.
4. 150–180 минут: деплой, README, текст для руководителя, список допущений.

## Проверка результата
Два исполнителя не видят задачи друг друга ни в UI, ни прямым запросом. Чужую задачу нельзя обновить по известному UUID. Нельзя сменить assignee/author/role. Запрещённый переход и возврат без непустого комментария отклоняются базой. Подмена actor/time и ручная запись истории запрещены. При конкурентных переходах проходит один, история согласована. Без сессии данных нет.
Проверить нескольких постановщиков, переназначение задачи и исчезновение доступа у прошлого исполнителя. История доступна обеим разрешённым ролям.
Минимальные интеграционные проверки этих правил важнее большого числа UI-тестов.

## Допущения для README
Принята — терминальное состояние. Повторное открытие и произвольный сброс статуса не реализовывать. Редактирование задачи не даёт обходить переходы. Исполнитель не редактирует остальные поля. Несколько постановщиков имеют одинаковые права. Правила переназначения и удаления задач с историей описать явно.
Не добавлять чат, файлы, уведомления, аналитику или realtime до выполнения обязательного.
